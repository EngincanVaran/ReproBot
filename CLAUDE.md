## Project state

**`TODO.md` at the repo root is the live tracker** — current pipeline status, every open bug per stage, blockers, and the prioritized next steps. Read it before planning work, and update it when something lands or a new issue is found. This file describes how the repo *works*; `TODO.md` describes what is *currently broken or missing*.

Implementation has started: **`ocr/` (PDF extraction), `reader/` (claims, hyperparameters, data_pipeline extraction, plus a validation retry loop), `coder/` (training-script generation), `runner/` (Docker-sandboxed execution), `orchestrator/` (the Coder↔Runner retry loop) and `critic/` (numeric fidelity verdicts, added 2026-09-14) are the pipeline stages with real code.** What is still design-only, per `docs/project-plan/ReproBot_Project_Plan.md`: the Report Generator. **`reader/` is now complete against its §1.2 spec** — all four specified fields plus `data_pipeline`.

**The chain is proven end to end, and it is now a loop, not a line.** A `dataset/` PDF goes through `ocr/` → `reader/` → `coder/` → `runner/`, and on a failure `orchestrator/` routes the Runner's triage back into the Coder as feedback and regenerates. Demonstrated against a deliberately reintroduced runtime bug (a scheduler reading a `self.optimizer` its `__init__` never assigned — valid Python, so `ast.parse` cannot catch it): the container run failed, Haiku triaged it `recoverable_error`, the Coder regenerated with that specific complaint, and the retry passed. `verdict: success`, one retry used. Two papers — Network In Network and Wide Residual Networks — have since been carried through the full orchestrated loop to `smoke`, both `success` on the first attempt.

**What "proven" does and does not mean here.** The CIFAR-10 runs are all `probe` or `smoke` stages — one epoch over a few hundred images — which establishes that a generated script *executes*, never that its number is *right*. A full-fidelity WRN-28-10 run measured at ~22 days on the dev machine's CPU. So no replication-fidelity claim exists for the CIFAR-10 set: that needs the Critic plus GPU compute. The CPU-sized `extra-papers/` targets below have real `full` numbers, first judged by hand and since 2026-09-14 re-judged by `critic/` with the same verdicts.

**The pipeline is no longer image-classification-only** (Engincan's explicit direction, 2026-09-13: ReproBot should handle multiple paper types). Since `dc5a541` the Coder writes a plain PyTorch loop for any supervised task, and the metrics contract is task-agnostic. Two small, CPU-trainable papers in `extra-papers/` test this: **Tang 2013** (MNIST, custom L2-SVM loss) and **Wijaya 2023** (Boston Housing, tabular regression). Tang produced the **first `full`-stage run** — and it collapsed into a dead network at ~89% error against a claimed 0.87%, with no stage noticing (see `docs/notes/tang-2013-ablation/`). Both have since run through `full` and give the project's **first two fidelity measurements, compared by hand**: Tang **0.82% vs 0.87%** (replicates, but only after a human changed one unstated guess, SVM `C` 1.0 → 0.1, from an ablation), and Wijaya **test RMSE 4.48 vs 3.02** (does not replicate on its one seeded split; the paper never states how its split was drawn). Wijaya's run was also the retry loop's first repair of a bug nobody planted. **Later the same day the Coder gained scikit-learn support** and three classical-ML papers ran through the Orchestrator: the Hsu/Chang/Lin SVM guide **96.625% vs 96.9%** (scikit-learn `SVC` reproduces all three of the paper's accuracies *exactly* at its settings; the gap is only the grid search's fold assignment picking C=γ=8 over 2), Fashion-MNIST's random forest **0.8773 vs 0.873** (mean of 5), and Frosst & Hinton's soft decision tree **95.11% vs 94.45%** — after a one-line manual fix: the paper prints Eq. 3 as −log of a never-positive quantity, the faithful implementation maximized cross-entropy, and that was caught by reading `docker logs` during the run. Numbers and caveats are in `TODO.md`.

Beyond the pipeline stages, the repo holds the project proposal, both progress reports, one-page handouts per stage, and a literature review built from 9 related papers, all under `docs/`.

**Repo layout convention — read before adding code:** each pipeline stage gets its own top-level folder at repo root — `ocr/`, `reader/`, `coder/`, `runner/`, `orchestrator/`, `critic/` today, with a report generator to come as another sibling — not nested under one unified `reprobot`/`src` package. This was an explicit user correction early on — don't reintroduce a `src/reprobot/`-style monolith. All stage folders share one root `pyproject.toml` / `uv.lock` / `.pre-commit-config.yaml`, unless a stage's dependencies are fundamentally unsyncable alongside the others (see the MinerU/Docling case below), in which case that stage's deps are documented but deliberately left out of the managed lock rather than breaking `uv sync` for everyone else.

**Build style:** one stage at a time, verified. Don't pre-scaffold stub packages for stages that haven't been asked for yet. Before calling a stage done, actually run `uv sync`, smoke-test scripts against real files (`dataset/` or `papers/`), and run `ruff check`/`ruff format --check`/`mypy --strict`/`pre-commit run --all-files` — this codebase has already surfaced real platform-specific breakage (see "Tooling" below) that only showed up by actually running things, not from reading the code.

### Orchestrator + agent delegation

Claude (the main session) is the **orchestrator** — Engincan talks to it directly; it decides when a task warrants a specialized subagent, dispatches one via the Agent tool, and appends what happened to `docs/agent-log.md` (who, what they were asked, what came back, summarized — full detail lives in the actual files/commits, not duplicated in the log). Not every task needs delegation; use judgment — trivial mechanical work (a rename, a one-line fix) is faster done directly.

**Established roles:**
- **Research Agent** (`general-purpose`, or `Explore` if it should be read-only) — surveys papers/notes/dataset/existing output, proposes a scoped design (e.g. "smallest useful first slice" for a new script). Doesn't write code.
- **Review Agent** (`general-purpose`, read-only) — critiques something before a costly or hard-to-repeat action (e.g. reviewed the VLM extraction prompt before an 8-paper batch API run). Concrete, specific recommended edits only, not generic advice.
- **Coding Agent** (`general-purpose`) — implements a scoped change; always verifies with `ruff check`/`ruff format`/`mypy --strict`/`pre-commit run --all-files`; instruments the actual code with detailed `loguru` logging (per-page/per-table/per-claim progress, not a single summary line) — Engincan has explicitly required this, not optional polish.
- **Validator Agent** (`Explore`, read-only) — audits existing output/coverage for completeness/quality issues; independent of a concurrent Coding Agent's work, so it can run in parallel with one.
- **Explainer** — usually Claude directly, not a subagent, since a fresh subagent would have to re-derive context Claude already has from the delegation it just orchestrated.

**Sequencing:** run independent agents in parallel (single message, multiple Agent tool calls); only sequence when there's a real dependency (e.g. claims extraction needed the VLM prompt fix to land first, so it ran after that Coding Agent, not alongside it). Don't force parallelism where one step's output is another's input.

**Before multi-step or costly work** (spawning several agents, an API-cost batch run), present the plan as clear numbered steps and wait for a go-ahead — Engincan has explicitly asked for this review-before-execute step more than once; don't skip it for anything non-trivial.

**Loops, but no open-ended agent:** the repo has two retry loops and both are bounded, deterministic Python — neither is an LLM deciding what to do next. `reader/pipeline.py` validates, routes each flag to the one extractor that owns it, re-extracts with the flag as feedback, and re-validates, capped at `max_retries=3` passes. `orchestrator/loop.py` runs the Coder, runs the result in `runner/`, and on a `recoverable_error` passes Runner triage's `suggested_fix` back into `CodeWriter.write(feedback=...)`, capped by a retry budget and a plateau guard. Each model call inside either loop is still single-shot: one call, structured output, done. The project plan's §1.3 recommends LangGraph for the Orchestrator; it is deliberately not used yet — even with the Critic's second conditional edge it is four pure decision functions and one readable loop. Revisit when the Report Generator or a human-escalation edge arrives — don't add graph machinery preemptively.

### Tooling

- **Python 3.13** (`.python-version`), **uv** as the package manager (`pyproject.toml` + `uv.lock`). `requires-python = ">=3.13"`.
- Dev tools: `ruff` (lint + format, line-length 100, double quotes), `mypy --strict`, `pre-commit` (hooks installed into `.git/hooks`; config in `.pre-commit-config.yaml`), and `pytest` (added 2026-09-14). Run `uv sync --group dev` plus whichever `--extra`s a stage needs. `tests/` holds replay tests for pure logic — `uv run --extra orchestrator pytest tests` — built from **real recorded curves**, not synthetic shapes; keep adding real cases, especially false positives found end to end.
- **Known platform trap, don't re-derive this from scratch:** the primary dev machine is an **Intel Mac (x86_64)**. No PyTorch release supports Python 3.13 **and** ships Intel-macOS wheels at the same time — PyTorch added 3.13 support at `2.5.0`, the exact release range where it dropped Intel-macOS wheels entirely (last Intel-mac wheel: `2.2.2`). Any torch-dependent tool (MinerU, Docling, and anything similar) cannot be `uv sync`'d into this project's main lock on this machine — declaring it as a project extra breaks `uv sync` for *everything*, since `uv.lock` resolves the union of all extras. Pattern to follow: keep such deps out of `pyproject.toml` entirely, write the integration code anyway, and document manual `pip install` instructions for whoever runs it on compatible hardware (see `ocr/README.md` for the live example with MinerU/Docling).
- **The trap is worse than "just don't use 3.13" — measured directly, don't re-derive:** dropping to Python 3.11 does get torch installed on this machine, but only `2.2.2` (the last Intel-mac wheel, as above). Current `transformers` (5.x) **requires torch >= 2.5**, and on finding 2.2.2 it does not error — it silently disables the PyTorch backend and reports "Models won't be available", so an HF `Trainer` script fails in a confusing way rather than at import. A working native combination on this host exists but is narrow and entirely legacy: `torch==2.2.2` + `transformers==4.46.3` + `accelerate<1.2` + `numpy<2` (torch 2.2.2 is compiled against NumPy 1.x and warns loudly under NumPy 2). Use that pin-set only for throwaway local smoke-testing of a generated script. **The real conclusion: running generated training scripts natively on this host is a dead end, which is exactly why `runner/` executes them in Docker** — the container has its own Linux Python, so none of this applies inside it. `runner/` is this trap's solution, not another instance of it.
- Secrets: `.env` (gitignored) holds `ANTHROPIC_API_KEY`; copy from `.env.example`. Scripts that need it call `dotenv.load_dotenv()` themselves.

### ocr/ — PDF extraction (implemented)

Four independent PDF→Markdown backends, same CLI shape (`--input`, `--output`, skips already-extracted papers), output to `ocr/output/<backend>/` (gitignored). Full detail, install commands, and the MinerU/Docling platform caveat are in `ocr/README.md` — read that before touching this stage, don't re-derive it:

- `pdfplumber_extract.py` — rule-based, no ML models. Verified working.
- `vlm_extract.py` — renders each page to a full PNG (pypdfium2) and sends it to Claude (`claude-sonnet-5`) in one call per page; genuinely reads figures (not text-only). Prompt does AutoP2C-depth figure description (every numerical element, caption cross-referenced), explicit two-column reading order, page-furniture exclusion, table/figure caption capture, and a compacted bibliography — see `docs/agent-log.md`'s Review/Coding Agent entries for the reasoning behind each. Verified working; run on the full 8-paper `dataset/` batch.
- `docling_extract.py`, `mineru_extract.py` — written, correct, but excluded from this repo's `uv.lock` per the platform trap above; not yet run by anyone. Someone else is running these on separate hardware.

Every pipeline module logs via `loguru`, not `print` (colorized, leveled, zero shared config — each imports its own `from loguru import logger`). The one deliberate exception is the **code `coder/` generates**: that script uses stdlib `logging`, since it runs standalone inside `runner/`'s Docker image and must not depend on this repo's tooling.

`ocr/` itself is extraction only — Markdown out, nothing structured. See `reader/` below for what consumes it.

### reader/ — structured extraction (complete: all 5 fields implemented)

Turns one paper's `ocr/output/vlm/<paper>.md` into structured data via Claude tool-use (forced structured JSON output, not free-text parsing), cross-checked by a validation step that can trigger a bounded retry loop. Full detail (class architecture diagram, loop diagram, a real caught-bug walkthrough) in `reader/README.md` — read that before touching this stage, don't re-derive it here.

- `base.py` — `Extractor[ResultT]` ABC (PEP 695 generic syntax): every extraction stage implements `name: ClassVar[str]` and `extract(markdown_text, client, feedback=None) -> ResultT`. Lets `pipeline.py` treat every stage uniformly (call `.extract()`, route validation flags back to the stage whose `.name` matches).
- `claims.py` — `ClaimsExtractor`. Extracts the paper's own reported results (metric, dataset, value, unit, source, optional `model_variant`), excluding baseline/prior-work rows from the same tables. Reuses the project plan's `Claim` shape (§1.2) plus `model_variant`.
- `hyperparameters.py` — `HyperparametersExtractor`. Extracts the paper's own training hyperparameters from both a dedicated table and "Implementation Details"/"Training Details" prose (value kept as a string, not float, so LR schedules survive).
- `method_summary.py` — `MethodSummaryExtractor`. Prose only (`problem`/`core_idea`/`novelty`/`summary`), deliberately carrying no numbers, hyperparameters, or architecture spec so the stages don't overlap and the validator doesn't flag phantom inconsistencies. Consumers are the Coder's context and the future Report Generator.
- `architecture_notes.py` — `ArchitectureNotesExtractor`. The field the Coder needs to write a real `nn.Module`. Three things make it different from its siblings: **figures are first-class source text** (the VLM's bracketed `[Figure N: ...]` blocks are often where structure actually lives — NIN's "three mlpconv layers + global average pooling" is stated in Figure 2's block, not in any table); **`specification` is a string, never a number**; and **`unstated_details` is required**, listing what the paper does *not* state. That last one matters more here than anywhere else — code has to run, so an invented-but-plausible channel count doesn't fail loudly, it trains the *wrong network* and reports a number for it. `key_equations` entries carry `is_own_method`, because a paper introducing a new layer prints the conventional formulation and often a rival's right beside its own; three unmarked equations is three plausible specs a code generator will pick one of. Prompt-level instructions to omit them did not work — the schema had to force the declaration.
- `data_pipeline.py` — `DataPipelineExtractor`. Extracts per-dataset preprocessing/augmentation/split info plus paper-level `reference_urls` (GitHub/dataset URLs). Deliberately does not guess: when a paper defers a detail to a citation without giving numbers, it records that fact rather than inventing plausible values — see `reader/README.md` for why.
- `tooluse.py` — shared request/response plumbing for all six Claude calls. Owns three *silent* failure modes, each producing a structurally valid but empty result indistinguishable from a clean run: `max_tokens` truncation, an all-empty payload, and a **double-encoded tool input** (the model returns the whole payload as a JSON string under one key on a clean `stop_reason: tool_use`). That last one is not hypothetical — it fires regularly on `data_pipeline`, and before the fix it silently reported zero datasets. Add new extractors through this module, not with hand-rolled `_tool_input` parsing.
- `validator.py` — `ExtractionValidator`. One more Claude call, given the full paper text plus every stage's combined output, that flags (does not fix) inconsistencies between stages or gaps vs. the paper. Iterates the results generically by stage name, so adding a new extractor needs zero changes here.
- `pipeline.py` — `ReaderPipeline`, the entry point (same `--input`/`--output`/skip-if-already-done CLI shape as `ocr/`'s scripts). Loads a paper's Markdown once, runs every stage once, validates, then loops: route flags to the one stage each belongs to, re-run only that stage with the flag folded into its prompt as feedback, re-validate — capped at `max_retries=3` total validation passes, finishes gracefully either way. Writes one combined `reader/output/<paper>.json` including `validation.flags`/`.attempts`/`.retried_stages`.
- Each extractor is an importable class (prompt + tool schema + parsing), not a standalone script — `pipeline.py` is the only entry point. A new extraction type (`architecture_notes`, ...) becomes one more `Extractor` subclass plus one more entry in `pipeline.py`'s default stage list, no other file changes.
- `reader/` is its own `pyproject.toml` extra (`anthropic` + `python-dotenv`), deliberately not reusing `ocr`'s `vlm` extra — it never touches a PDF or renders a page image, only reads `ocr/`'s Markdown output.

### coder/ — training-script generation (implemented)

Turns one paper's `reader/output/<paper>.json` **plus** that paper's `ocr/output/vlm/<paper>.md` into a single self-contained **plain-PyTorch** training script for **any supervised task** — image classification, other classification, tabular regression — via one Claude tool-use call. Full detail in `coder/README.md` — read that before touching this stage.

- **No HuggingFace `Trainer`, deliberately.** It was dropped when the stage was generalized (`dc5a541`). Its model contract (`pixel_values` in, logits out) fits regression and custom losses badly, and it silently applies defaults no paper states. That second reason was proven on the spot: the old NIN script inherited `Trainer`'s gradient clipping at `max_grad_norm=1.0`, which the paper never uses — the faithful plain-loop version, without it, diverged. Don't reintroduce `Trainer`, `accelerate`, Lightning or Keras.
- **The model family picks the library.** Classical estimators (SVMs, trees, forests, k-NN, logistic regression, naive Bayes, scikit-learn MLPs) are built with **scikit-learn**, every hyperparameter by name — never re-implemented in PyTorch (`SVC` wraps LIBSVM, so a LIBSVM paper can reproduce exactly). Paper-era **library-version defaults** are set explicitly and disclosed (e.g. SVC `gamma` 'auto' before 0.22, RandomForest 10 trees before 0.22). Flags with no meaning for an estimator are documented no-ops; loss/epoch metrics may be `null`; a claim averaged over N runs/folds is reproduced as N runs, with `num_runs`/`run_values` added to `metrics.json`. No xgboost/lightgbm/catboost in the image yet.
- **Neural models always PyTorch, whatever framework the paper used** (including trees trained by gradient descent). A Keras paper's unstated settings inherited Keras defaults, so the prompt requires matching them in code where cheap (Adam ε 1e-7, Glorot init, BatchNorm momentum 0.99 / ε 1e-3, `fit()` batch size 32) and disclosing every difference in `assumptions`.
- **`task_type` is inferred** from the targeted claim's metric and dataset, not extracted by the Reader, and recorded in `coder_output.json`.
- **Data loading order is explicit:** `torchvision.datasets` for images; for tabular, OpenML via `fetch_openml(data_home=args.data_dir)` pinned by `data_id` **first**, a direct URL only if the dataset is on neither. The ordering exists because the first tabular run chose CMU StatLib's Boston Housing URL, which now returns HTTP 403 to every client. The script must also **assert the fetched dataset is the intended one** (name, row/column counts) before training — a wrong OpenML `data_id` doesn't fail, it trains on a different dataset. A paper that gives split sizes but not the method gets a seeded split, disclosed.

- **Input precedence is explicit and three-level.** Rank 1 is `reader_output` — above all `architecture_notes`, which is the primary source for the model's structure. Rank 2 is the paper's OCR Markdown, for corroboration and anything the extraction missed. Rank 3 is the model's own pretrained memory of an architecture, **permitted only when disclosed** in the output's `assumptions`. Rank 3 is allowed rather than forbidden on purpose: a code generator cannot decline to answer the way an extractor can — something has to be written where a missing channel count goes — so the rule is "guess visibly", not "never guess". Both documents together are ~18k tokens, so they fit in one call with no retrieval machinery.
- **The prompt enforces what `architecture_notes` records:** implement only `key_equations` marked `is_own_method` (a paper prints rival formulations for contrast, and implementing one silently builds the wrong layer); skip components tagged as baselines; never supply a depth formula `depth_or_scale` says is absent; answer every `unstated_details` entry in `assumptions`. Verified on Network In Network, deliberately rather than WRN — a wide ResNet would be rebuilt correctly from memory and prove nothing. The script built a real mlpconv cascade with zero `nn.Linear`, and excluded both decoy equations by name.
- `base.py` — `CodeWriter[ResultT]` ABC, same shape as `reader/base.py`'s `Extractor`: `name: ClassVar[str]`, `write(reader_output, paper_markdown, client, feedback=None) -> ResultT`. `orchestrator/loop.py` passes Runner triage's `suggested_fix` in through `feedback` on a retry, exactly as `reader/`'s loop does for validation flags via `Extractor.extract()`.
- `script_writer.py` — `TrainingScriptWriter`. One `claude-sonnet-5` call, `max_tokens=16384` with an explicit `stop_reason` check (this repo has hit `max_tokens` silently twice; never again). Emits the script plus bookkeeping: targeted claim, architecture/dataset/hyperparameters used, and an `assumptions` list.
- `pipeline.py` — the only entry point, same `--input`/`--output`/skip-if-done CLI shape as `reader/`. Writes three files to `coder/output/<paper>/`: `train.py`; `reproduce.sh`, generated **deterministically by template, not by the model**, so it cannot invent a flag `train.py` doesn't define; and `coder_output.json` with the bookkeeping. `run()` accepts `feedback` and threads it to the writer.
- **`coder/` never executes anything and never imports torch** — it calls the Claude API and writes files. The generated script's own heavy deps (torch, torchvision, pandas, scikit-learn) live inside `runner/`'s Docker image, deliberately kept out of this repo's `uv.lock` — the same platform-trap avoidance already used for `ocr/`'s MinerU/Docling. Its extra is just `anthropic` + `python-dotenv`, identical to `reader`'s.
- **Three deterministic, zero-LLM-cost gates** before a script is accepted: `ast.parse()` (a `SyntaxError` writes the file to `.py.invalid` and marks the run failed rather than emitting broken Python), a literal check that every required CLI flag appears in the generated text, and (since 2026-09-14) a **progress-contract gate**: the script must write the learning-curve history (`REPROBOT_PROGRESS` marker + `metrics.<mode>.history.jsonl`, one JSON record per epoch/repetition with `chance_metric`, `target_value`, `loss_lower_bound`) that `runner/`'s live check-ups read — missing it raises `ScriptContractError` and the Orchestrator retries without a Docker run. The tool schema also requires `model_family` (`neural`/`classical`), which gives classical estimators a data-scaled `capped` stage in `reproduce.sh`. Capped subsets must be seeded random and stratified, never the first N rows (label-sorted files).
- **Target-claim selection:** `--claim-id` overrides it; without one, the model picks the paper's headline claim and must justify the choice in `claim_selection_reasoning`, logged loudly — a wrong pick silently reproduces the wrong number.
- **The generated script's CLI is a load-bearing contract**, enforced by gate 2 — all nine of `REQUIRED_CLI_FLAGS`: `--epochs`, `--max-train-samples`, `--max-eval-samples`, `--batch-size`, `--lr`, `--output-dir`, `--metrics-output`, `--seed`, `--data-dir`. Defaults are the paper's real values, so a bare invocation reproduces the paper's setup while `reproduce.sh`'s cheaper modes just fast-forward it. **`--data-dir` must default to exactly `./data`**: `runner/` bind-mounts a shared dataset cache there, and a regenerated script that once pointed elsewhere silently re-downloaded CIFAR-10 — the same stage took 2000 s instead of 169 s, with no error. It was added to the contract for that reason. The script writes a fixed-shape `metrics.json` (documented in `coder/README.md`) whose `metric`/`unit` are copied verbatim from the targeted claim, so the Critic can diff against `reported_value` with no unit conversion. Since generalization the contract is task-agnostic: `train_metric`/`eval_metric` (the claim's *own* metric per split) replace `train_accuracy`/`eval_accuracy`, plus `task_type` and `higher_is_better` — a bare `value` of 4.0 means nothing without knowing whether lower is better. Old accuracy-keyed files still parse; nothing reads the new keys strictly.

### runner/ — Docker-sandboxed execution (implemented, verified in Docker)

Executes a paper's generated training script inside a container and reports what happened. Full detail in `runner/README.md` — including an explicit Status section separating what is verified from what has never run.

- **The interface is `reproduce.sh <mode>`, nothing else.** Runner never builds a `python` command and never passes a `--flag`; it picks one of `probe`/`smoke`/`capped`/`full`, or the Critic's extra-seed modes `seed2`/`seed3` (full again with another seed; not part of the escalation ladder). This was an explicit user redesign, and the point is that Runner stays paper-agnostic — a future paper whose script needs entirely different arguments changes only its own `reproduce.sh`. Don't "helpfully" reintroduce flag-passing.
- `Dockerfile` — `python:3.11-slim` + CPU-only torch (pinned `2.5.1`, bare not `+cpu`, so it resolves on both x86_64 and aarch64), plus pinned `pandas`, `scikit-learn` and `scipy` for tabular papers — installed in the **same pip command** as `numpy==2.1.3`, so a transitive upgrade fails the build instead of silently moving numpy. `transformers`/`accelerate` remain only because the older NIN/WRN scripts still import `Trainer`. Nothing generated is `COPY`d in: `coder/output/<paper>/` is bind-mounted at run time, so the image stays static across every Coder regeneration and results come back out through the same mount rather than `docker cp`.
- `docker_runner.py` — `DockerRunner`. Escalating gates that stop at the first failure, per-stage timeouts, log capture/truncation, metrics parsing. **The timeout is the subtle part:** `subprocess.TimeoutExpired` kills only the `docker run` *client* while the container keeps running inside `dockerd`, so every run gets an explicit `--name` and a matching `docker kill` on timeout. `TimeoutExpired` also attaches partial output as raw *bytes* even in text mode — decoded defensively, or every timeout would crash the handler reporting it.
- `triage.py` — one Haiku 4.5 call, and **only** on a genuine non-timeout failure, to classify `recoverable_error` (bug in the generated script) vs `environment_error` (container/dependency problem). Success and timeout are decided mechanically with no LLM call at all; that's deliberate, not an oversight. **A failed download is `recoverable_error` when the network works but one source refused** (HTTP 403/404/5xx) — a rewritten script can fetch the data elsewhere; only a container with no network at all is `environment_error`. The prompt used to file every download failure under `environment_error`, which made the Orchestrator stop with zero retries on a dead URL one regeneration would have fixed. `suggested_fix` has four rules: never change what is being reproduced (no "use a similar dataset"), one fix not a menu, no API it's unsure still exists, and no specific identifier (dataset id, URL, version) unless it appears in the log — a triage model confidently recalled Boston Housing as OpenML `data_id=506`, which is a different dataset.
- `pipeline.py` — the only entry point, same `--input`/`--output`/skip-if-done shape as the other stages. `--max-stage` escalates (default `capped`); `--mode` runs exactly one; `full` is never reached by default because it needs a GPU.
- **Its own extra is just `anthropic` + `python-dotenv`** — Runner shells out to the `docker` CLI via `subprocess`, so it needs no Docker SDK and no torch on the host. This is the platform trap's *solution*: all ML deps live inside the image, where the host's Python version is irrelevant.
- **Stage timeouts are calibrated against a measured run**, not estimated: probe 2700 s / smoke 900 s / capped 1800 s / full 86400 s. A cold dataset cache dominates the first run (~1707 s of a 1774 s probe was the CIFAR-10 download), which is why `probe` carries the large budget and later stages assume a warm cache. An earlier 1200 s estimate would have timed out on the very first run — indistinguishable from a hung script.
- **Live check-ups (`checkups.py`, 2026-09-14) judge whether training is healthy while it runs.** A watcher thread beside the blocking `subprocess.run` reads the history file every few seconds; six pure rules (`non_finite`, `loss_below_lower_bound`, `worse_than_chance`, `no_progress`, `stuck_at_chance`, `diverged`) with per-stage allow-lists, persistence and chance-based margins can kill the container by name (same path as a timeout) and end the stage `halted` with evidence; the rules run once more after exit for short stages. The Orchestrator retries a halt with that evidence as feedback (no triage call). Verified by replaying real curves (Tang collapse halted, all healthy runs untouched) and live in Docker (a sign-flipped soft tree killed at epoch 1 of 40). **Keep rules conservative** — end-to-end testing already caught one false positive (`no_progress` in `capped` halted a correct soft tree whose loss sat at ln 10 while accuracy was 3x chance), fixed by restricting it to `full` and requiring no gain over chance. Check-ups judge health, not fidelity: a healthy run far from the paper's number is the Critic's job. Scripts generated before the contract write no history and fall back to exit-code-only judgement.
- **Known sharp edges** (documented, not fixed): the image is not byte-reproducible (`python:3.11-slim` is a moving tag; pin by digest); the container runs as root, which macOS hides but a Linux host won't; `--memory`/`--cpus` are exposed but unset by default, because an arbitrary cap produces exit 137 that looks exactly like a script crash.

### orchestrator/ — shared-memory state + the Coder↔Runner retry loop (implemented)

The stage that makes ReproBot a loop rather than a line. Full detail in `orchestrator/README.md`.

- `state.py` — `ReproState`, the project plan's §1.2 shared-memory object implemented faithfully. `critic_output` was reserved from the start and now holds the Critic's latest judgement, its extra seed values and every earlier judgement; `fidelity_retry_count` and each attempt's `critic_verdict` record the fidelity side. `history` is an append-only audit log of structured entries (timestamp/stage/event/detail), which is what lets the loop answer "have we already tried this".
- `loop.py` — the retry loop as four **pure** decision functions (`decide_after_run`, `decide_after_syntax_error`, `decide_after_regeneration`, `decide_after_critic`) plus a thin driver. Keeping the routing pure is why all seven terminal verdicts are unit-testable with no Docker and no API key.
- **The check order in `decide_after_run` is load-bearing, don't reorder it:** `environment_error` is checked *before* the retry budget, because regenerating a script cannot fix a broken container — routing it as a code bug would burn the whole budget on a fix that was never the problem. A `timeout` likewise stops rather than retries: `runner/` deliberately produces no triage for timeouts, and a slow-but-correct script must not be "fixed" into a different one.
- **Plateau guard** (project plan §2.1): before spending a Docker run on a regenerated script, it's compared line-wise to its predecessor with `SequenceMatcher(autojunk=False)` — `autojunk` must stay off, it discards repeated lines and measured 0.9975 vs. 0.7625 on the same pair. Ratio ≥ 0.98 stops early rather than burning budget on a fix that isn't changing anything. The real ratio is logged every retry so the threshold is tunable from data.
- `pipeline.py` — the only entry point, same CLI shape as the other stages, plus `--retry-budget`, `--plateau-threshold`, `--use-existing-script` (seeds attempt 1 from a script already on disk instead of paying to regenerate it), and the Critic's `--no-critic` / `--seed-budget` / `--fidelity-retry-budget`.
- **Deliberately NOT LangGraph**, despite the project plan's §1.3 recommendation. The state object is exactly §1.2-shaped and the routing is isolated in pure functions, so migrating stays mechanical. Revisit when the Report Generator or human escalation adds real branching, not before.
- **Execution and fidelity verdicts stay separate.** `state.verdict` says how far execution got (`success`, `timeout`, …); `critic_output.verdict` says whether the number matches. A fidelity `fail` can still be an execution `success`.

### critic/ — fidelity verdicts (implemented 2026-09-14)

Judges a reproduced number against the paper's claim. **v1 (built) is the arithmetic half: no LLM, no Docker, no network** (project plan §2.5). **v2 (next, agreed 2026-09-14) adds the LLM half the plan also specifies:** a Sonnet code review after every full run (script vs. paper extraction, with cited evidence) and concrete diagnosis feedback to the Coder on a fail. The LLM never changes the arithmetic verdict. Engincan expects the Critic to be a real agent that reviews code and runner output, not only a number check. Full detail in `critic/README.md`; the plan is in `TODO.md`.

- `claims.py` — merges duplicate claims (one result printed in prose, table and figure): same normalised metric (R-Squared/R2/R-square → `r2`), dataset and unit; values within the coarser reporting precision; no train/test conflict; no model-name conflict (variant words minus split/filler words and location references like "Table 3", numbers otherwise kept — "depth 40" ≠ "depth 22"). Keeps the most precise member as canonical. Never edits Reader output. Verified across 9 papers / 243 claims: only Wijaya's four groups merge.
- `judge.py` — `tolerance = max(2 × uncertainty, reporting precision)`. Uncertainty is the measured run spread when ≥2 runs exist (claim is a mean → `std·√(2/n)`, else `std·√(1+1/n)`), else binomial test-set noise for accuracy-like metrics, else none. Verdicts: `pass` (within tolerance, or better than the claim → `exceeds_claim`), `fail` (worse, with an uncertainty estimate → recommends guided retry), `inconclusive` (worse, no uncertainty estimate → recommends more seeds), `not_evaluated` (run did not succeed, no value, stage other than `full`, unknown claim). `guided_retry_feedback` lists only the Coder's recorded unstated `assumptions` as revisable and requires `fidelity retry:` entries.
- `pipeline.py` — CLI over an Orchestrator `state.json` (`--state`, `--write` stores `critic_output`) or a reader JSON + metrics file (`--reader-json`, `--metrics-json`, `--extra-metrics`). Output to `critic/output/` (gitignored).
- **In the Orchestrator:** `inconclusive` → `seed2`/`seed3` once, only if the full run took ≤ `--seed-budget` (1800 s) and `reproduce.sh` has seed modes; `fail` → ONE guided fidelity retry per paper (`--fidelity-retry-budget`), only with unstated choices recorded and retry budget left. Bounded on purpose: more retries would fit unstated hyperparameters to the test split.
- **The five real `full` results re-judged:** Tang pass (0.82 vs 0.87%, ±0.19 binomial), SVM guide pass (96.925 vs 96.9%, ±0.55), Fashion-MNIST RF pass + exceeds (0.8773 vs 0.873, ±0.0018 from 5 runs), soft tree pass + exceeds (95.11 vs 94.45%, ±0.46), Wijaya inconclusive (RMSE 4.48 vs 3.02, one run, no noise model) → seeds. These are replay tests in `tests/test_critic.py`.

## What ReproBot is

ReproBot (`docs/proposal/ReproBot.pdf` — the original project proposal) is a four-agent pipeline, coordinated by a central **Orchestrator** over **shared memory**, that reads an ML paper PDF and produces a verified replication report:

```
PDF paper
    │
    ▼
Orchestrator (shared memory state)
    │
    Reader (pdfplumber + VLM)   → method summary, claims, datasets, hyperparameters
    Coder (HuggingFace Trainer) → self-contained training script
    Runner (Docker sandbox)     → executes script, captures metrics + error traces
    Critic                      → compares reproduced metrics vs. paper's claimed numbers,
                                   emits pass/retry/fail verdict, feeds targeted fixes back to Coder
    │
    ▼
Structured Markdown replication report (claim-by-claim comparison + gap analysis)
```

The Orchestrator drives the Critic↔Coder retry loop until results clear a confidence threshold or the retry budget is exhausted. Initial evaluation scope per the proposal: **20 image-classification papers** (not a broad multi-topic benchmark) — a legibility trade-off, since a single domain allows a much stricter numeric tolerance in the Critic's pass/fail logic. **Superseded in part on 2026-09-13:** Engincan decided ReproBot must handle multiple paper types, so `coder/` and `runner/` were generalized; CIFAR-10 remains the main evaluation set, but the stages must not assume images. Proposed 4-month timeline: Reader (M1) → Coder+Runner+Orchestrator skeleton (M2) → Critic+refinement loop+report generation (M3) → evaluation+ablation+demo (M4). Planned stack per the proposal: LangChain (agent framework), pdfplumber/pdf2image (PDF parsing), LLaVA/GPT-4V (vision-language), Docker (sandboxing), Gradio (demo), Weights & Biases (tracking).

`docs/project-plan/ReproBot_Project_Plan.md` expands this into an implementation-ready plan — feasibility assessment, per-agent tool/model specs, a de-risked timeline, risk register, and a compute/cost budget. It supersedes the original proposal's rougher edges (e.g. recommends LangGraph over plain LangChain, standardizes on Claude models across agents rather than the proposal's OpenAI/open-source language) — treat it as the primary reference for implementation decisions, and the proposal PDF as historical context for *why* the project exists.

## papers/ — reference PDFs

The 9 papers analyzed in `docs/literature-review/` are stored as PDFs directly in `papers/`, renamed to their full titles (not arXiv IDs) for readability:
- `MLAgentBench - Evaluating Language Agents on Machine Learning Experimentation.pdf` (Huang et al., 2023) — foundational agentic-ML-experimentation benchmark; motivates ReproBot's Reader/Coder/Runner/Critic role separation.
- `PaperBench - Evaluating AI's Ability to Replicate AI Research.pdf` (Starace et al., 2025, OpenAI) — the gold-standard replication benchmark (20 ICML papers, 8,316-leaf-node rubric); primary target for evaluating ReproBot.
- `Paper2Code (PaperCoder) - Automating Code Generation from Scientific Papers in Machine Learning.pdf` (Seo et al., 2025) — closest architectural cousin (Planning→Analysis→Coding maps to Reader→Coder); generates code but never executes it.
- `AutoP2C - An LLM-Based Agent Framework for Code Repository Generation from Multimodal Content in Academic Papers.pdf` (Lin et al., 2025) — closest single system to ReproBot's full pipeline shape (multimodal parsing + execution + iterative debug loop); its debug loop stops at "runs and looks aligned," with no numeric-tolerance Critic verdict.
- `AutoReproduce - Automatic AI Experiment Reproduction with Paper Lineage.pdf` (Zhao et al., 2025) — most sophisticated direct competitor; the "paper lineage" (mine cited papers/repos for implicit detail) idea is an open extension point for ReproBot's Reader/Coder.
- `Agent Laboratory - Using LLM Agents as Research Assistants.pdf` (Schmidgall et al., 2025) — new-research-generation system; architectural inspiration (Literature Review→Experimentation→Report Writing), complementary not competing.
- `The AI Scientist - Towards Fully Automated Open-Ended Scientific Discovery.pdf` (Lu et al., 2024) and `The AI Scientist-v2 - ....pdf` (Yamada et al., 2025) — new-research-generation, complementary; v2's VLM figure-feedback loop and tree-search retry strategy are relevant design references.
- `MLR-Copilot - Autonomous Machine Learning Research based on Large Language Models Agents.pdf` (Li et al., 2024) — new-research-generation; its retrieval-augmented (HuggingFace prototype code/model/dataset) implementation pattern is a candidate technique for ReproBot's Coder.

When adding a new paper to this set: (1) download/rename the PDF to its full title in `papers/`, (2) add a deep-dive subsection to `docs/literature-review/PaperAgent_LiteratureReview.md` (and wire it into that file's TOC, capability gap matrix, and citation-differentiator table), (3) add a template-consistent entry to `docs/literature-review/Paper_Summaries.md` with real extracted numbers, (4) update `docs/literature-review/Introduction_and_Literature_Review.md`'s prose and references list if it changes the positioning narrative, (5) update `docs/literature-review/Evaluation_Metrics_Comparison.md` if the new paper introduces its own evaluation metric worth folding into the shared taxonomy.
