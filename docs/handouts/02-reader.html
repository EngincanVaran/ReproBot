Understanding the paper reader/

Built · working

Text is still just words. This stage turns the paper into facts a program can look things up in — what it claims, what it built, and what it never bothered to say.

What goes in, what comes out

Input
The paper as textfrom stage 1
What happens
Five separate readingsplus a checker that re-reads them
Output
One structured filefacts a program can look up

The key points

  • It asks five separate questions, not one big one. What problem does this paper solve? What model does it build? What results does it claim? What settings did it train with? How was the data prepared?
  • Every single fact comes with a receipt. Each extracted value records where it came from — “Table 1, page 5” — so any number can be traced back and checked.
  • It writes down what the paper does not say. Genuinely the most important part, and the reason is on the right.
  • A checker re-reads everything and flags problems. Whatever it flags gets re-done, with the complaint included so the second attempt addresses it specifically. Up to three rounds.
  • Numbers are stored as text. Sounds odd, but a setting like “0.1, dropped by 0.2 at epochs 60, 120, 160” is not one number — and “not stated” has to stay sayable.

Why point three matters most

One of 12 gaps recorded for Network In Network
"Exact number of feature maps per layer: the paper says only 'the same number as in the corresponding maxout network', deferring the actual numbers elsewhere."

The next stage has to write real code, and code needs a real number here. If this gap were quietly filled with a plausible guess, the result would train perfectly and report a confident number for the wrong model. Recording the gap keeps that decision visible instead of silent.
