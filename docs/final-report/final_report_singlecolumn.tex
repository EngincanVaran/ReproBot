\begin{abstract}
ReproBot reads a machine learning paper's PDF and returns a replication report. It transcribes
the paper with a vision-language model, extracts its claims and experimental setup into
structured fields, generates a self-contained training script, executes that script in a Docker
sandbox while watching the learning curve for signs that training is not healthy, judges the
reproduced number against the paper's claim with explicit arithmetic, reviews the generated code
against the paper, and renders the result as Markdown. Failures at either end --- a script that
crashes and a number that misses --- are fed back to the code generator through one bounded
retry loop. This report presents the finished system and everything it has measured. Five papers
spanning five model families were reproduced at their own full settings and all five passed,
two of them beating the paper's own number. Three of those papers were then carried from PDF to
report three times each: 9 of 9 runs reproduced their claim, and every run reached the full stage
on its first attempt. The same protocol was then run on a paper the pipeline had never seen,
whose task has no train/test split at all, and passed 3 times out of 3. A further eleven papers
were put through the whole loop in one batch, several of them on a rented GPU: four reproduced
their claim, four did not, and three could not be judged. Those four are the first replication
failures this project has reported, and they matter more than their number --- a system that can
return \emph{does not replicate} is the thing that makes its passes worth anything. The central
finding is about where the remaining disagreement comes from: every difference between runs of
the same paper traced to exactly one detail that paper never states, and we could name it each
time --- a fully specified protocol gave three independently generated scripts bit-identical
values, while an unstated cross-validation shuffle, an unstated data split and an unstated
repetition count each moved the result in a way we can explain. A loop-on/loop-off ablation
shows the retry loop changed 1 of 5 verdicts, and that the system's real defence against
publishing a wrong number is not the retries but the guards: a live check-up that halts an
unhealthy run, a Critic that refuses to rule on one, and a review that can block a number that
matched for the wrong reason.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Most published machine learning results are reproducible in principle and expensive to reproduce
in practice. The method is in the prose, the numbers are in the tables, and the thousand small
decisions in between --- which split, which initialisation, which library version's defaults ---
are in neither. ReproBot automates the whole path: paper in, replication report out, with every
guess it had to make written down.

The system is a pipeline of seven stages and two bounded retry loops, coordinated through one
shared-memory state object. It is complete: every stage in the project plan exists, has run on
real papers, and is verified by execution rather than by inspection. This report is
self-contained --- it assumes no earlier reading --- and leads with results, because the
results are the point.

Its contributions are:

\begin{itemize}
  \item \textbf{Five full-fidelity replications across five model families}, each judged by
    arithmetic rather than by eye, with two reproductions better than the paper's own number
    (Section~\ref{sec:results}).
  \item \textbf{Eleven more papers in one batch}, four reproducing their claim and four not ---
    the first failures this system has reported rather than had planted in it
    (Section~\ref{sec:batch}).
  \item \textbf{A repeatability measurement}: three papers carried from PDF to report three
    times each, 9 of 9 passing, plus a fourth paper the pipeline had never seen, 3 of 3
    (Section~\ref{sec:repeat}).
  \item \textbf{The report's main finding}: run-to-run variance is a property of the paper, not
    a defect of the system, and in every case we could name the single unstated detail
    responsible (Section~\ref{sec:unstated}).
  \item \textbf{An explicit, model-proof verdict}: the tolerance is arithmetic over the claim's
    own precision and the run's own measured spread, and no model can change it
    (Section~\ref{sec:verdict}).
  \item \textbf{The project plan's headline ablation}, loop on against loop off, reported
    honestly including where the loop bought nothing (Section~\ref{sec:experiments}).
  \item \textbf{Two documented paper sets}, one CPU-sized and one GPU-bound, with a per-paper
    statement of how far each has got and where its evidence lives (Section~\ref{sec:sets}).
\end{itemize}

\textbf{A note on provenance, because this report mixes two kinds of evidence.} Everything in
Sections~\ref{sec:results5} to~\ref{sec:experiments}, apart from Section~\ref{sec:batch}, was
re-derived for this report from run data committed to the repository, and the files are named
where the numbers are. The eleven-paper batch of Section~\ref{sec:batch} was run on a rented GPU
box and on a second contributor's machine; its state files are not in the repository, so every
figure in it is reported \emph{as recorded in the project tracker} and is marked as such.

\textbf{The loop.} Two feedback edges close it. On an execution failure, a small model classifies
the failure as a bug in the generated script or a problem with the container; a script bug is
routed back to the Coder as a specific complaint and the script is regenerated. On a fidelity
failure, the Critic's verified findings and the Coder's own list of unstated guesses become the
feedback for one guided retry. Both edges are bounded: a retry budget, a single fidelity retry
per paper, and a plateau guard that compares each regenerated script with its predecessor and
stops early when the ``fix'' is not changing anything.

\textbf{The parts that must not be wrong are tested.} The pure logic --- the Critic's arithmetic,
the loop's four decision functions, the seven check-up rules, the Coder's gates, the
pass-blocking rule and the report renderer --- is covered by 135 replay tests, built from real
recorded learning curves and real recorded reviews rather than synthetic shapes, including every
false positive found end to end.

\textbf{The dashboard, and how a run is started.} \texttt{viewer/} is a Streamlit app over the
pipeline's own outputs: a per-paper status table, then tabs for the Reader's five extractions,
the generated script, the Runner's stages and live learning curve, the Critic's verdict and
review, and the rendered report. It is deliberately thin. Every button calls the matching
stage's published entry point unmodified --- \texttt{run\_vlm()}, \texttt{reader}'s and
\texttt{coder}'s \texttt{run\_pipeline()}, the Orchestrator's CLI --- so nothing a paper does
through the dashboard differs from doing it from a shell, and the dashboard can never produce a
verdict the command line would not. Its \texttt{full\_run} helper carries one paper through
every stage as a background job that survives a restart, with each stage skipping work already
on disk, and can place the Orchestrator step either in local Docker or on a rented GPU box over
SSH: the code and that paper's inputs are copied over, the run is started under
\texttt{nohup} so a dropped connection does not kill it, and its outputs are copied back on
every poll so the curve fills in live. The Runner has a matching CUDA image, selected by one
flag, differing from the CPU image only in which index its \texttt{torch} wheels come from.

\textbf{What the stages run on.} The Runner's interface is \texttt{reproduce.sh <mode>} and
nothing else --- it never builds a \texttt{python} command and never passes a flag --- so a paper
whose script needs entirely different arguments changes only its own \texttt{reproduce.sh}. The
four modes escalate: \texttt{probe}, a few optimiser steps; \texttt{smoke}, one epoch on a small
slice; \texttt{capped}, a few epochs on a small slice; and \texttt{full}, the paper's own setup.
The Critic may additionally ask for \texttt{seed2} and \texttt{seed3}, which are \texttt{full}
again with another seed.

\subsection{Fidelity: five papers, five model families}
\label{sec:results5}

Table~\ref{tab:fidelity} is the result this report is built on, because it is the one whose
evidence is committed alongside it. Five papers were reproduced at their own full settings ---
not a reduced proxy --- and judged by the arithmetic of Section~\ref{sec:verdict}. All five
passed. Two reproductions are better than the paper's own number by more than the tolerance
band, which the Critic records as \texttt{exceeds\_claim}. Figure~\ref{fig:curves} shows four of
the implementations learning. A sixth paper was added to the table later, under the harder
condition described in Section~\ref{sec:unseen}: the pipeline had never seen it.

Two of the five needed a human correction before their final run, and the report says which:
Tang's unstated SVM penalty was changed from the common default $C = 1.0$ to $C = 0.1$ after a
six-configuration ablation, and the soft-tree paper's misprinted loss was implemented as its
evident intent. Both are in Table~\ref{tab:problems}. The other three ran unassisted.

\textbf{Tang: an MLP with a margin loss.} The network trained for the paper's own 400 epochs,
training error falling to 0.062\% (Figure~\ref{fig:curves}a), and the test set --- evaluated once,
at the end --- gave 0.82\% against the paper's 0.87\%: five test images out of 10{,}000, well
inside the $\pm$0.1857 that binomial noise on a 10{,}000-image test set allows.

\textbf{The SVM guide: the cleanest exactness test available.} Because scikit-learn's
\texttt{SVC} wraps the same LIBSVM the guide itself used, the library \emph{is} the method, and
at the paper's own settings the reproduction matches its reported accuracies exactly
(Table~\ref{tab:svmexact}). Everything that remains is model selection:
Figure~\ref{fig:curves}b shows the cross-validation surface the generated script searched, with a
broad ridge of settings above 96\% and the paper's own choice one cell away from the search's.

The paper states the tree's depth and essentially nothing else about training, so the generated
script chose and recorded a value for each missing setting. Test accuracy passed the paper's
94.45\% at epoch 11 and finished at 95.11\% (Figure~\ref{fig:curves}d). No setting was chosen on
the test set, so a result 0.7 points above the claim with every guess disclosed is a comfortable
reproduction rather than a lucky one.

\textbf{Wijaya: the one that needed more than one run.} The first full run of the housing-price
network gave test RMSE 3.1285 against the claimed 3.02 --- worse than the claim, with no noise
model to say whether that mattered. The Critic returned \texttt{inconclusive} and asked for
seeds instead of ruling. Two more full runs gave 3.0283 and 2.9520, and the re-judgement was
\texttt{pass} at a mean of 3.03629 with a tolerance of $\pm$0.2044 that was now measured rather
than assumed. A system that ruled on one number would have called this paper a failure at 3.13,
or a success at 2.76, depending only on which run you happened to see.

\subsection{Eleven papers in one batch, and the first reported failures}
\label{sec:batch}

The results above are six papers chosen because they are cheap. The batch in
Table~\ref{tab:batch} is the opposite kind of evidence: eleven papers put through the whole
pipeline --- transcription, extraction, generation, the orchestrated loop with the Critic, and a
rendered report --- in one day, several of them on a rented GPU through the dashboard's remote
path. \textbf{Four reproduced their claim, four did not, two could not be judged at all, and one
was still training when the batch was written up.}

\textbf{The four failures are the most valuable rows in this report.} Until this batch, every
\texttt{fail} verdict the project held came from a run that was not allowed to stand: one from a
bug we planted on purpose to test the Critic's diagnosis (a swapped train/validation unpacking
in the Wijaya script), and one from an ablation leg discarded for an unrelated infrastructure
fault --- a second single-shot Tang generation that scored 1.17\% against a claimed 0.87\%, a gap
of 0.30 against a band of $\pm$0.1857, which Section~\ref{sec:experiments} reports because the
disagreement is itself a finding. Neither was a paper the system had been asked to replicate and
honestly reported as not replicated. These four are. That distinction is the whole point of
building the Critic as arithmetic: \textbf{a replication system that cannot return
\emph{does not replicate} has not established anything by returning \emph{does}}, and until this
batch ours had never had to.

\textbf{The failures are not all the same kind of failure, and the spread between them is the
useful part.} fastText misses by more than six tolerance bands, which is a result: something
about that reproduction is wrong or the paper's 91.5\% depends on something it does not say, and
either way the gap is far too large to be noise. Tang's CIFAR-10 claim misses by 2.25 points,
from the same paper and the same generated-code path whose MNIST claim passes --- the clearest
demonstration in this report that a verdict is about a claim, not about a paper. TCN misses by
0.24 against a band of 0.20, which is a near miss that the arithmetic nonetheless calls, and
correctly: the rule is fixed in advance so that it cannot be relaxed once the number is known.

\textbf{And then the uncomfortable one.} XGBoost reproduced test AUC 0.8292 against a claimed
0.8304 --- a gap of 0.0012, or 0.14\% of the claim --- and \texttt{fail}ed, because three runs
agreed so closely that the measured band came out at $\pm$0.0005. This is a real property of the
rule and it is worth stating rather than hiding: \textbf{a tolerance derived from a tight
measured spread can turn a near miss into a failure, and the same gap with one run instead of
three would have been judged \texttt{inconclusive} and sent for more seeds.} We think the rule is
still the right one --- a band that grows when the evidence is weaker and shrinks when it is
stronger is exactly what the uncertainty of the gap \emph{is}, and a fixed relative tolerance
would have let a 0.14\% miss through on a paper whose own numbers are stable to a tenth of
that. But a reader who wants to call this row a near-reproduction rather than a failure is
reading the same arithmetic we are, and the printed tolerance is what lets them. Two things
would sharpen it: the spread of three runs is a three-sample estimate of $\sigma$ and
systematically underestimates it, and the claim's own uncertainty --- which the paper does not
report --- is not in the band at all.

\textbf{Two of the three unjudged rows are the system refusing, not crashing.} Breiman was
stopped before a script was even paid for, because the Reader had extracted no claims and a
script that targets a claim nobody can find can never be judged. Network In Network was halted
four separate times by the live check-ups while training, which is the guard working exactly as
designed and the honest statement that this paper does not yet train: \texttt{not judged} is the
correct answer, and it is a different answer from \texttt{fail}.

\subsection{A paper the pipeline had never seen}
\label{sec:unseen}

Those three papers are the papers this project debugged against, which is the obvious objection
to a 9-of-9 result. So the same protocol --- three runs, full loop, review on run~1 --- was run
the next day on a fourth paper that had never been transcribed, read or coded before:
\emph{Isolation Forest} \cite{liu2008iforest}. \textbf{3 of 3 runs passed, each reaching
\texttt{full} on its first attempt with no retry}, in 20 to 33 seconds end to end.

The target was chosen to be hard to hit by luck. The paper states twelve AUC values; Pima's
0.67 is a mid-range one, where the near-ceiling rows (Shuttle 1.00, Breastw 0.99) would pass
almost any implementation --- and it is one of the paper's own \emph{weak} rows, where isolation
forest loses to the ORCA baseline's boldfaced 0.71. The Reader noticed that and annotated the
claim. The task shape is one nothing else in this project has: there is no train/test split at
all. The forest is fit unsupervised on the whole contaminated dataset and the labels are used
only afterwards, to score an AUC. The Coder produced a working script for that on the first
attempt, having never seen the paper.

\textbf{The SVM guide's mechanism is worth stating exactly, because it is counter-intuitive.}

paper specifies its protocol completely, ReproBot's output is deterministic across generations.
That is the strongest available evidence that the variance seen elsewhere is not the Coder being
unreliable.

\subsection{Does the code match the paper? The Critic's review}

The verdict says whether the number matched; it cannot say whether the number was produced the
way the paper describes. A second Critic call reads the Reader extraction, the paper, the
line-numbered script, the Coder's recorded assumptions, the learning curve and a filtered runner
log, and returns findings --- each one a claim about the code with a paper quote and script lines
attached --- plus ranked hypotheses for any gap. Deterministic guards then decide what reaches the
Coder: a cited number must appear in the material, a paper quote must exist in the paper, script
lines and snippets must exist in the script, and a proposed fix may not introduce a technique the
paper never mentions. Findings that fail a guard are dropped, and the count of dropped findings is
printed in the report.

The reviewer is \texttt{claude-opus-5} on evidence, not preference. On a Wijaya script with a
deliberately swapped train/validation unpacking, Sonnet~5 missed the bug three times --- even with
the log stating the two split sizes --- and misdiagnosed it as a missing early-stopping rule,
which made the Coder add checkpoint selection that the paper never mentions. Opus found the swap,
the loop fixed it, and the next review returned \texttt{faithful}: a fidelity \texttt{fail} at
4.76 became a \texttt{pass} at 3.40 against 3.02, in eleven minutes.

\textbf{The review can also block a pass, which is the most recent thing it learned to do.} A
matching number proves nothing about a paper if the script that produced it is not the paper's
method, and the case that forced this was real: a regenerated Pang \& Lee script invented 1,400
keyword-planted ``reviews'' instead of fetching the corpus, and scored 92.8\% against a claimed
82.9\%. The arithmetic had no way to object --- the number was better than the claim. So a pass
whose review carries a \texttt{major\_deviations} rating, or any \emph{verified} high-severity
deviation or implementation bug, is now routed as a correctness retry when the budget allows and
is otherwise reported as \texttt{not established} rather than as a reproduction. The rule is
deliberately narrow and deliberately deterministic: it recomputes from the stored review, so an
old state file renders the same way today; it never touches the arithmetic verdict itself; and
medium-severity or unverified findings never block, because an honest pass must survive a
reviewer's minor quibble. It was replayed against the real GCN and Kim reviews from the batch of
Table~\ref{tab:batch}, whose passes stand.

\section{How a Verdict Is Made}
\label{sec:verdict}

The fidelity verdict is arithmetic. It makes no model call, opens no network connection and starts
no container, which means no model can argue its way to a pass:
\[
  \text{tolerance} = \max(2u,\ p),
\]
where $p$ is the claim's own reporting precision and $u$ the run's uncertainty. Precision is read
from the claim as printed: a claim of 3.02 is precise to $\pm 0.005$. Uncertainty comes from the
run itself where the run can supply it --- if two or more runs exist,
from their measured spread, as $\sigma\sqrt{2/n}$ when the claim is itself a mean and
$\sigma\sqrt{1 + 1/n}$ when a single-run claim is being compared with our mean --- and otherwise,
for an accuracy-like metric, from the binomial noise of a test set that size. When neither is
available there is no uncertainty estimate, and the band collapses to the claim's own precision.

Four verdicts follow, and each carries a consequence:

\begin{itemize}
  \item \texttt{pass} --- within tolerance, or better than the claim beyond it, which is recorded
    separately as \texttt{exceeds\_claim}. A pass whose code review shows the script was not
    doing what the paper describes is reported as \texttt{not established} instead.
  \item \texttt{fail} --- worse than the claim beyond tolerance, \emph{with} an uncertainty
    estimate. If the Critic's review found verified problems the paper itself states, this becomes
    a normal retry; otherwise it spends the single guided fidelity retry.
  \item \texttt{inconclusive} --- worse than the claim, but with no uncertainty estimate at all.
    The system asks for more seeds instead of ruling. This fired on Wijaya and changed the
    outcome.
  \item \texttt{not\_evaluated} --- nothing comparable: the run did not succeed, produced no value,
    stopped short of \texttt{full}, or targeted a claim the Reader does not have.
\end{itemize}

Table~\ref{tab:tolerance} is the honesty column of this report. A \texttt{pass} at $\pm$0.00175 on
0.873 and a \texttt{pass} at $\pm$0.2044 on 3.02 are not the same statement, and a bare verdict
hides the difference. So the tolerance is printed everywhere the verdict appears, and when the
band exceeds 10\% of the claim the report adds an explicit warning. An earlier escalation of the
same Wijaya claim passed at a mean of 3.3292 with a tolerance of $\pm$1.0680 --- 35\% of the claim
--- and its report says in as many words that the result is \emph{consistent with} the paper rather
than a close match. Tang's $\pm$0.1857 on a claim of 0.87\% is the same situation in a different
guise: a test error that small is simply not measurable to better than about a fifth of itself on
10{,}000 images.

The XGBoost row is the same honesty pointing the other way, and it is the one this report would
most like a reader to argue with. $\pm$0.0005 on an AUC of 0.8304 is the narrowest band here by a
factor of three, because three runs happened to agree to four decimals --- and it is what turned a
gap of 0.0012 into the \texttt{fail} of Table~\ref{tab:batch}. Nothing was tuned to produce that
outcome: the rule was fixed before the run, which is the only property that makes any of these
verdicts worth reading. But the band is a three-sample estimate of a standard deviation, which
underestimates on average, and it contains no term for the uncertainty of the paper's own
number, which the paper does not report. Both corrections would widen it.

That is a thin result and it should not be dressed up. Four of five papers paid for the loop ---
a Critic call each, plus the seed runs it is entitled to --- and got the verdict single-shot had
already reached. Two of the five loop-on numbers were also human-assisted (Tang's hand-changed
$C$, the soft tree's hand-corrected loss), so the loop-on arm is better described as ``the loop
plus the human attention this project actually gave these papers''.

\textbf{What the loop did contribute, robustly, is the guard rails rather than the retries.} Note
what did \emph{not} happen on the soft tree: the pipeline did not report 7.8\% accuracy as a
replication result. A live check-up killed the container 6.18 seconds in, with its reason
recorded --- the training loss had reached $-0.8361$, below the loss's own lower bound of zero ---
and the Critic then refused to judge a halted run, returning \texttt{not\_evaluated}. Both of
those fired with retries switched \emph{off}. On this evidence, ReproBot's main defence against
publishing a wrong number is its guards; the retry loop is a comparatively rare repair path.

\textbf{And the variance is real.} Tang was run twice in the loop-off arm with the identical
prompt and pinned claim. The kept leg scored 0.85\% and passed; the discarded leg --- discarded
for an unrelated infrastructure fault, and reported here because the disagreement is itself the
finding --- scored 1.17\% and \emph{failed}, a gap of $+0.30$ against a band of $\pm$0.1857. Two
different scripts, either side of the tolerance. One single-shot generation per paper is
therefore a noisy measurement, and a five-paper, one-generation-per-arm design cannot resolve
differences this size. Settling the question needs $k \approx 5$ independent generations per
paper per arm.

\textbf{The set's first fidelity verdicts exist, and they are passes.} \emph{Wide Residual
Networks} ran at its own full configuration on a rented RTX 4090 in about 3.4 hours for roughly
\$1.50 and reproduced 3.83\% test error against the paper's 4.00\% (median of five) --- inside
the $\pm$0.39 that two standard errors of binomial noise on 10{,}000 test images allow, and the
review returned \texttt{faithful}. \emph{DenseNet} reproduced 5.37\% against 5.24\%, inside
$\pm$0.45. Both are recorded in the project tracker rather than in this repository; what is
committed here is the recorded WRN metrics, as a replay fixture for the check described next.

\textbf{That WRN run is also where a guard came from.} The reported 3.8261\% of 10{,}000 test
images is not a whole number of mistakes --- but it is exactly 382 of 9{,}984, which is 78
batches of 128. The script had been scoring 9{,}984 images and reporting 10{,}000, because the
final partial batch was being dropped. A deterministic check now catches that class of error by
arithmetic alone (Table~\ref{tab:problems}).

\textbf{Three caveats, because this is easy to over-read.} First, the two passes are single
seeds on rented hardware, not a repeated measurement: nothing here has the three-run evidence
Section~\ref{sec:repeat} has. Second, the WRN script was written by an earlier version of the
Coder, before the plain-PyTorch rewrite, so it does not exercise the generator this report
otherwise describes and has still to be regenerated and sent round the loop. Third, four of the
eight papers have no verdict and one of those four --- Network In Network --- has been
\emph{tried} at \texttt{full} four times and halted by a live check-up every time. The reason the
rest of the set is still open is arithmetic rather than pessimism: the \texttt{full} \emph{Wide
Residual Networks} configuration measures at about 22 days on the development CPU, against about
a minute and a half to seventy minutes for each paper in the CPU set, so every number in this
subsection costs rented GPU time.

\section{Honest Limits}
\label{sec:limits}

The following are the limits of what this report establishes. They are stated plainly because a
replication system that oversells itself is worse than useless.

\begin{itemize}
  \item \textbf{The widest result in this report is not evidenced in this repository.} The eleven
    papers of Table~\ref{tab:batch} ran on a rented GPU box and on a second contributor's machine;
    their state files, scripts and logs are not here, so none of those rows was re-derived the way
    the rest of this report was. They are reported as the project tracker records them, and that
    is a weaker kind of evidence than everything else on these pages.
  \item \textbf{One claim per run.} Fashion-MNIST has 74 extracted claims and one was tested;
    Isolation Forest 24 and one. Every generated report lists the untested remainder as
    \texttt{not tested}, so the denominator is on the page --- but twelve repeated runs are four
    claims, not four papers replicated.
  \item \textbf{The GPU set's two passes are single seeds on rented hardware}, one of them from a
    script written by a superseded version of the Coder, and four of its eight papers still have
    no verdict. One of those four has been tried at \texttt{full} four times and halted every
    time.
  \item \textbf{Most of the replicated papers were chosen because they reproduce on CPU in
    minutes.} A 9-of-9 pass rate is a statement about the pipeline running unattended on tractable
    papers, not a success rate on an arbitrary paper --- and the batch that was not chosen that way
    reproduced four claims out of eight judged.
  \item \textbf{Two of the five original fidelity numbers were human-assisted} --- one unstated
    hyperparameter changed after an ablation, one misprinted loss corrected --- and both are
    marked as such wherever they appear.
  \item \textbf{A tolerance can be narrower than the thing it is judging.} XGBoost's
    \texttt{fail} rests on a $\pm$0.0005 band estimated from three runs; three samples is a poor
    estimate of a standard deviation, and the paper's own uncertainty is not in the band at all.
  \item \textbf{The ablation is too thin to settle its own question}: five papers, one generation
    per arm, with two loop-on numbers human-assisted and three loop-on states captured on a
    zero-retry day. Three runs is enough to see whether a paper varies, not to estimate how much.
  \item \textbf{Re-runs overwrite \texttt{state.json}}, so a previous run's evidence is lost
    unless it was written to a separate output directory.
  \item \textbf{Retries regenerate the whole script} instead of patching the faulty lines, which
    makes each retry more expensive and less targeted than it needs to be.
  \item \textbf{Review ran on one generation per paper} in the repeated batches, so a deviation
    present only in the other two generations would not have been caught by the reviewer.
  \item \textbf{The dashboard does not yet show the loop.} It is merged and it can start a whole
    paper locally or on a GPU box, but it displays Runner, Critic and report output only --- not
    the Orchestrator's attempts, its retry feedback or the Critic's seed escalation, which are
    exactly the parts a demonstration most wants to show.
  \item \textbf{One dataset carries an ethical caveat.} Boston Housing includes a feature derived
    from the proportion of Black residents per town \cite{harrison1978hedonic}; it is used here
    only because the replicated paper used it.
\end{itemize}

\section{What Is Next}
\label{sec:future}

\textbf{Patch, do not regenerate.} A retry currently rewrites the whole script, which is why a
regeneration can change an unstated hyperparameter that had nothing to do with the failure. The
loop should edit the faulty lines and hold every other disclosed guess fixed unless the feedback
concerns it.

\textbf{More than one claim per paper.} The coverage table is the clearest gap in this report.
Breiman alone offers 13 independent per-dataset claims and Isolation Forest twelve AUC values,
which would multiply the evaluation without multiplying the compute. Tang is the proof that this
is not bookkeeping: its two claims disagree, and a system that tested only the first would have
reported the paper as reproduced.

\textbf{Chase the four failures.} Each one is now a concrete, bounded question rather than a
gap in coverage --- why fastText is four points short, whether TCN's 0.24 is the implementation
or the paper, whether XGBoost's 0.0012 survives more seeds. A failure the system can name is the
cheapest research it has ever offered us.

\textbf{Make Network In Network train.} It is the one paper that has been attempted at
\texttt{full} and never got there, halted four times by the check-ups. Until it does, the oldest
paper in the CIFAR-10 set has no verdict for a reason the system itself diagnosed.

\textbf{The two remaining boosting libraries.} \texttt{xgboost} is now in both Runner images,
which is what let the XGBoost paper run at all; \texttt{lightgbm} and \texttt{catboost} are what
one selected paper still waits on.

\textbf{Close the last silent failure.} The XGBoost fidelity retry ended with the Coder returning
no script three times in a row, most likely a token ceiling reached without being reported --- the
same class of defect the Reader's three guards already cover, in the one stage that does not yet
have it.

\textbf{Keep every run's evidence, in one place.} Making each run's state immutable rather than
overwriting it would have preserved two results this project has already lost --- and the eleven
papers of Table~\ref{tab:batch} would be evidence in this report rather than a citation to a
tracker if the remote path copied its states back into the repository by default.

\textbf{Show the loop.} The dashboard can now start a whole paper and watch it train on a rented
GPU, but it still does not display the Orchestrator's attempts, its retry feedback or the
Critic's escalation --- the parts of this report a demonstration would most want on screen.

\section{Conclusion}
\label{sec:conclusion}

ReproBot carries a paper from PDF to a judged replication report without supervision. Five papers
across five model families reproduced their published numbers at the papers' own settings, two of
them beating the published figure; three were carried end to end three times each and passed 9
times out of 9; a fourth, which the pipeline had never seen and whose task has no train/test split
at all, passed 3 out of 3. Eleven more went through the whole loop in a single batch, four
reproducing their claim and four not. The verdict behind every one of those is arithmetic over the
claim's own precision and the run's own measured spread, printed with its tolerance so that a wide
pass cannot masquerade as a close match --- and, since the batch, narrow enough in one case to
turn a 0.14\% miss into a failure, which we report rather than round away.

Those four failures are what the rest of this report was for. A replication system that only ever
answers \emph{yes} has not answered anything, and until this batch ours had never been made to
say otherwise about a paper it was asked to replicate. Saying it required the whole apparatus: a
tolerance fixed before the run so it cannot be relaxed afterwards, a check-up that halts a run
rather than reporting its number, a reviewer that can block a pass whose code was not the paper's
method, and a verdict of \texttt{not judged} that is kept distinct from a verdict of
\texttt{fail}.

The result we did not expect is the one we would keep. When runs of the same paper disagreed, the
disagreement was never mysterious: it was one sentence the paper did not write. A paper that
states its protocol completely gave three unrelated scripts bit-identical numbers; a paper that
omits whether its cross-validation folds are shuffled moved its own selected hyperparameters and
its test accuracy; a paper that gives split sizes but not split assignment moved its RMSE
continuously across a range that contains its claim; a paper that never says whether its headline
AUC is one run or an average changed not the value but the strength of the evidence behind it, and
the reviewer named that ambiguity before an independent run demonstrated it. Reproducing a result
automatically turns out to be a good way of finding out precisely what a paper forgot to say ---
and the system's most valuable habit is not its retry loop but its refusal to report a number it
cannot stand behind.
